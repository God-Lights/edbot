# GL 연결 서버

**로그인은 GL 계정, 데이터(전적·랭킹)는 개인 서버**에 두는 서버 방식이다.
안드로이드 서버 앱과 로컬 서버(exe)에서 켤 수 있다. iPad 서버 앱은 나중에 지원한다.

| | 이름만 (open) | GL 연결 (linked) | 공식 (gl) |
|---|---|---|---|
| 로그인 | 이름 | GL 계정 | GL 계정 |
| 로그인 확인 | 없음 | 공식 서버가 대신 확인 | 공식 서버 |
| 전적·랭킹 | 개인 서버 | 개인 서버 | 공식 서버 |
| 인터넷 | 필요 없음 | 로그인할 때 필요 | 필요 |

## 왜 이렇게 하나
- GL 계정을 확인하려면 GL Account 의 비밀 키가 필요하다. 이 키를 개인 서버에 넣으면 서버를 돌리는 누구나 키를 볼 수 있다.
- 그래서 **공식 서버(edgame-api)가 중개자**가 된다. 개인 서버는 GL 비밀 키도, 사용자의 공식 로그인 토큰도 받지 않는다.
- 개인 서버가 받는 것은 승인된 사용자의 **GL id·아이디·닉네임**뿐이다. 이메일은 넘기지 않는다.

## 흐름
1. 개인 서버가 처음 한 번 공식 서버에 등록해 **서버 id**와 비밀값을 받는다.
   - `POST /api/link/register`
   - 받은 값은 데이터 폴더(AuthStore)에 저장한다.
2. 사용자가 로그인을 누르면, 개인 서버가 공식 서버에 로그인 요청을 만든다 (`POST /api/link/start`).
   - 요청을 만들 때 서버 id 와 비밀값으로 서버를 확인한다.
3. 브라우저에 공식 승인 페이지(`/link?id=`)가 열린다.
   - 사용자는 GL 계정으로 로그인하고, **"「서버 이름」(서버 id abcd-ef01-2345)에 들어갈까요?"** 를 승인한다.
   - 공식 서버가 아니라는 경고도 같이 보여 준다.
4. 개인 서버가 결과를 받는다 (`POST /api/link/poll`).
   - 결과는 한 번만 받을 수 있고, 10분이 지나면 만료된다.
5. 개인 서버는 **자기 세션 토큰**을 만들어 준다. 이 토큰은 7일 동안 쓴다.
   - 앱(iPad): 기존 기기 로그인(`/api/auth/start` → 브라우저 → `/api/auth/poll`)과 똑같다. 그래서 앱은 고치지 않았다.
   - 웹·안드로이드 앱(웹 화면):
     - `/auth/login` 을 누르면 공식 승인 페이지로 간다.
     - 승인하면 `/auth/done` 으로 돌아오고, 개인 서버가 `cmd_session` 쿠키를 준다.

## 서버 설정
- **안드로이드 서버 앱**:
  - 설정의 **로그인**에서 **GL 연결**을 고른다.
  - **주인 GL 아이디**를 적는다.
  - **GL 계정 없는 사람도 받기**를 켜거나 끈다.
- **로컬 서버**:

  ```bash
  commander-server --auth linked --link-owner <주인 GL 아이디> [--link-guests]
  ```

- **게스트(GL 계정 없는 사람)**:
  - 끄면 GL 계정이 있어야 방을 만들고 들어간다. `/api/server` 의 authMode 는 `gl` 이다.
  - 켜면 이름만으로도 논다. 대신 전적은 GL 계정끼리 한 판만 남는다. authMode 는 `hybrid` 다.
  - 학번+이름 게스트 방은 공식 서버와 같다.
- `/api/server` 의 `linked: { owner }` 로 GL 연결 서버인지 알린다.
  - 웹 로비에는 "GL 연결 서버 · 이름" 띠가 나온다.
  - 주인으로 로그인하면 띠에 "서버 관리" 단추가 생긴다.

## 주인 관리 (`/server-admin.html`)
- 브라우저에서 주인 GL 계정으로 로그인하면 쓸 수 있다.
- **사람 목록**: 이 서버에 GL 계정으로 들어온 사람의 닉네임, 아이디, 레이팅, 판 수, 마지막 접속.
- **막기·풀기**:
  - 막힌 사람은 다시 로그인하거나 새 방에 들어올 수 없다. 이미 받은 세션도 쓸 수 없다.
  - 지금 하던 판은 끝까지 한다.
- **랭킹 처음부터**:
  - 선수 표와 판 기록을 `backups/reset-<시각>/` 에 옮겨 두고 비운다.
  - 다시 보기는 남긴다.
- 쿠키로 들어온 POST 는 같은 주소에서 보낸 것만 받는다. 다른 사이트가 몰래 보내는 것을 막기 위해서다.

## 공식 서버 쪽
- `GL_ACCOUNT_KEY` 가 있는 서버(공식·개발)에만 `/api/link/*` 와 `/link` 가 열린다.
- **등록 제한**: 한 IP 에서 한 시간에 10개까지.
- **비밀값**: 서버 비밀값과 결과를 받는 비밀값은 해시만 저장한다.
- **서버 막기**: 문제 있는 서버는 막을 수 있다 (`AuthStore.linkBlock`). 아직 관리 화면은 없다.
- **돌아갈 주소**: 승인 뒤에는 개인 서버의 `/auth/done` 으로만 보낸다. 다른 경로나 사이트로 보내는 데 쓰이지 않게 막았다.

## 서버 앱 엔진 (안드로이드·iPad)
- 숨은 웹뷰의 `Request` 는 `cookie`·`origin` 헤더를 버린다.
- 그래서 엔진은 이 두 헤더를 `x-commander-cookie`·`x-commander-origin` 으로 이름을 바꿔 넘긴다. 서버는 `auth.ts` 의 `cookieHeader`·`originHeader` 로 둘 다 읽는다.
- 다른 사이트의 브라우저는 이 이름의 헤더를 보낼 수 없다. CORS 가 허락하지 않기 때문이다.
- 안드로이드 서버(NanoHTTPD)는 같은 이름의 헤더를 하나만 남긴다. 그래서 응답마다 쿠키를 하나만 보낸다.

## 남은 약점
- LAN 접속은 http 다. 그래서 같은 와이파이에서 가로채는 공격까지는 막지 못한다. 지금 로컬 서버와 같은 수준이다.
- 서버 이름은 아무나 정할 수 있다. 그래서 승인 페이지에 서버 id 와 경고를 같이 보여 준다.
